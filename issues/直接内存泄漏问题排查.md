## CMS 堆外内存参数配置

Netty 用的是**堆外内存（Direct Memory）**，这块内存不归 CMS 管，但需要单独限制大小并且要配合堆内 GC 参数一起调优，否则容易出现堆外内存泄漏或 OOM 但堆内存却看起来正常的情况。

```properties
-Xms4g -Xmx4g
-Xmn1500m
-XX:MaxDirectMemorySize=2g

# CMS GC 相关
-XX:+UseConcMarkSweepGC
-XX:+UseParNewGC
-XX:CMSInitiatingOccupancyFraction=70
-XX:+UseCMSInitiatingOccupancyOnly
-XX:+CMSParallelRemarkEnabled
-XX:+CMSScavengeBeforeRemark

# 避免Full GC时Direct内存跟着OOM，提前触发GC回收DirectByteBuffer的引用
-XX:+DisableExplicitGC   # 谨慎使用，见下方说明

# GC日志（排查内存问题必备）
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-XX:+PrintGCApplicationStoppedTime
-Xloggc:/path/to/gc.log
-XX:+UseGCLogFileRotation
-XX:NumberOfGCLogFiles=5
-XX:GCLogFileSize=100M
```

几个关键点需要特别注意：

**1. 关于 `DisableExplicitGC` 要谨慎**
 Netty 的 `PooledByteBufAllocator` 依赖 JVM 的 `System.gc()` 作为兜底手段，在 Direct Memory 快耗尽时触发老年代 GC 从而回收 `DirectByteBuffer`（通过 Cleaner 机制释放堆外内存）。如果你开了 `-XX:+DisableExplicitGC`，反而会导致 Direct Memory 泄漏更快触发 OOM。**除非你已经确认 Full GC 频繁触发是因为其他代码手动调用 `System.gc()`，否则不建议禁用。**

**2. MaxDirectMemorySize 和堆内存的关系**
 Direct Memory 释放依赖堆内的 `Cleaner` 对象被 GC 回收，所以堆内 GC 不及时（比如老年代增长慢、CMS 触发不及时）会间接导致 Direct Memory 也涨得慢释放。`CMSInitiatingOccupancyFraction=70` 这种主动提前触发 CMS 的配置就是为了让堆内堆外内存能同步及时回收。

**3. Netty 自身也有相关系统参数可以配合调优**

```bash
-Dio.netty.maxDirectMemory=2147483648    # 与JVM参数保持一致，单位字节
-Dio.netty.allocator.type=pooled         # 使用池化分配器，减少频繁分配释放
```

## Spring Cloud Gateway 报direct out of memory问题修复gc

Spring Cloud Gateway 基于 Netty，`io.netty.util.internal.OutOfMemoryError: failed to allocate direct memory` 这个问题通常不是简单调大内存就能解决的，本质多是**内存泄漏**或**池化内存碎片化 / 未及时释放**导致，光加 GC 参数只能缓解不能根治。按下面思路排查+修复。

### 1. 先判断是"真的不够用"还是"泄漏了"

```bash
# 查看当前进程direct memory实际使用量
jcmd <pid> VM.native_memory summary   # 需要开启 -XX:NativeMemoryTracking=summary

# 或者通过监控指标(Gateway默认暴露的actuator metrics)
curl http://localhost:port/actuator/metrics/jvm.buffer.memory.used?tag=id:direct
curl http://localhost:port/actuator/metrics/netty.eventLoop.pendingTasks
```

如果 direct memory 持续增长不回落（即使业务量平稳），基本可以判定是**泄漏**，不是配置不够。

### 2. Direct Memory 相关 JVM/Netty 参数配置

```bash
-Xms4g -Xmx4g
-XX:MaxDirectMemorySize=2g

# Netty自身参数(比JVM参数优先级更高，建议保持一致)
-Dio.netty.maxDirectMemory=2147483648

# 关键：不要禁用显式GC，Netty依赖System.gc()做兜底回收
# 千万不要加 -XX:+DisableExplicitGC

# 开启Netty内存泄漏检测(排查阶段用，生产环境用SIMPLE或PARANOID会有性能损耗)
-Dio.netty.leakDetection.level=PARANOID
```

**内存泄漏检测级别说明：**

| 级别     | 采样率 | 用途                               |
| -------- | ------ | ---------------------------------- |
| DISABLED | 不检测 | 生产默认(部分版本)                 |
| SIMPLE   | 1%     | 生产环境推荐，日志会打印`LEAK`警告 |
| ADVANCED | 1%     | 打印详细堆栈，方便定位泄漏代码     |
| PARANOID | 100%   | 仅排查阶段用，性能损耗大           |

排查阶段先开 `ADVANCED`，日志里搜 `LEAK: ByteBuf.release()`，能直接定位到泄漏发生的代码堆栈。

### 3. CMS GC 配合调优

```bash
-XX:+UseConcMarkSweepGC
-XX:+UseParNewGC
-XX:CMSInitiatingOccupancyFraction=65
-XX:+UseCMSInitiatingOccupancyOnly
-XX:+CMSParallelRemarkEnabled
-XX:+CMSScavengeBeforeRemark
```

`CMSInitiatingOccupancyFraction` 调低一点（65左右），让老年代更早触发 CMS GC，间接加快 DirectByteBuffer 的 Cleaner 回收速度，避免堆内堆外内存回收不同步导致堆外内存"看起来"泄漏。

### 4. Netty 分配器优化

```yaml
# application.yml
spring:
  cloud:
    gateway:
      httpclient:
        pool:
          type: elastic       # 或 fixed，看并发量决定
          max-connections: 1000
          acquire-timeout: 5000
```

```bash
# 使用池化分配器(默认已经是pooled，但可以显式确认)
-Dio.netty.allocator.type=pooled
-Dio.netty.allocator.numDirectArenas=8
```
